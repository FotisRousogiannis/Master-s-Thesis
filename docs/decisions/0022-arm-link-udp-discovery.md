# ADR-0022: Πακέτο `arm_link` για εύρεση του Pi και μέτρηση της σύνδεσης (UDP)

- **Κατάσταση:** Αποδεκτή
- **Ημερομηνία:** 2026-11-16
- **Επεκτείνει:** ADR-0021 (σύνδεση υπολογιστή ↔ Pi)

## Πλαίσιο
Το πάνελ «Σύνδεση» του Arm Studio έψαχνε το Pi στη σταθερή διεύθυνση `10.42.0.2` ή ως `armpi.local`. Στην
πράξη το Pi (Raspberry Pi OS, NetworkManager) παίρνει διεύθυνση με DHCP από το προφίλ «shared» του υπολογιστή
(σήμερα `10.42.0.116`), και στο WiFi θα έχει άλλη. Άρα το Pi δεν βρισκόταν (γνωστό πρόβλημα Π1). Δεν υπήρχε
επίσης τρόπος να μετρηθεί η ποιότητα της σύνδεσης: καθυστέρηση, απώλειες, jitter.

## Εναλλακτικές
### Εύρεση
| Επιλογή | Υπέρ | Κατά |
|---|---|---|
| Σταθερή IP / κράτηση DHCP | καμία αλλαγή στον κώδικα | ρύθμιση σε κάθε δίκτυο ξεχωριστά |
| mDNS (`όνομα.local`) | έτοιμο στο Raspberry Pi OS | δεν περνά πάντα σε δίκτυα πανεπιστημίου και σε Docker· εξαρτάται από το hostname |
| **UDP broadcast σε κάθε δίκτυο του υπολογιστή** | δουλεύει σε όποια IP και όποιο δίκτυο, με τον ίδιο server που κάνει και το ping | χρειάζεται server στο Pi· κάποια δίκτυα κόβουν το broadcast |

### Πώς το βρίσκει το Arm Studio (`arm_gui`, πακέτο ROS) το `arm_link` (απλό πακέτο Python)
1. **`PYTHONPATH` στο `software/docker/compose.yaml`**: ο κώδικας ισχύει αμέσως, χωρίς εγκατάσταση.
2. `pyproject.toml` + `pip install -e`: πιο τυπικό, αλλά χρειάζεται βήμα εγκατάστασης σε κάθε container και στο Pi.

## Απόφαση
- Ξεχωριστό πακέτο **`software/arm_link`** (καθαρή Python, χωρίς ROS), ώστε να τρέχει ίδιο στο PC και στο Pi:
  `Ping` (12 bytes), `LinkStats`, interface `Transport` με `FakeTransport` (tests) και `UdpTransport`,
  `LinkProbe` (PC), `EchoServer` (Pi), `discovery` (broadcast σε κάθε δίκτυο, με `psutil`).
- Στο Pi ο `EchoServer` τρέχει ως υπηρεσία systemd **`arm-link-echo`** (θύρα UDP 9999).
- Το πάνελ «Σύνδεση» βρίσκει το Pi πρώτα με UDP broadcast (μετά την παλιά σταθερή IP και mDNS) και δείχνει
  την ποιότητα της σύνδεσης (γραμμή «Σύνδεση (UDP)», κουμπί «Έλεγχος σύνδεσης»).
- Το `arm_gui` βρίσκει το `arm_link` με **`PYTHONPATH`** (επιλογή 1, απόφαση του Φώτη).

## Αιτιολόγηση
Το broadcast είναι ο μόνος τρόπος που δεν χρειάζεται ρύθμιση ανά δίκτυο, και ο ίδιος server εξυπηρετεί και
τη μέτρηση. Το interface `Transport` αφήνει χώρο για άλλη μεταφορά (π.χ. serial) χωρίς αλλαγή στον `LinkProbe`.
Το `PYTHONPATH` είναι μία γραμμή, και το πακέτο είναι ακόμα σε ενεργή ανάπτυξη.

## Συνέπειες
- Το Pi πρέπει να τρέχει την υπηρεσία `arm-link-echo` (`docs/setup/raspberry_pi.md`). Χωρίς αυτήν, το πάνελ
  δείχνει «δεν απαντά» στη γραμμή UDP, και η εύρεση πέφτει στις παλιές μεθόδους.
- Στο Docker image μπαίνουν `python3-psutil` και `iproute2`· το `PYTHONPATH` απαιτεί επανεκκίνηση του container.
- Μετρημένο στο Ethernet (2026-11-16): 0 % απώλειες, RTT 0.17 ms, max 0.41 ms (`docs/measurements/link/`).
  Το WiFi δεν έχει μετρηθεί· δίκτυα που κόβουν το broadcast χρειάζονται τη διεύθυνση με το χέρι.
- Ο server απαντά σε οποιονδήποτε στο τοπικό δίκτυο (μόνο ηχώ, χωρίς εντολές)· εντολές κίνησης θα θέλουν
  έλεγχο αποστολέα.
- USB (2026-11-16): δεν προχωρά. USB-C gadget = και τροφοδοσία του Pi· USB-TTL = νέο `SerialTransport`.
  Αν χρειαστεί, το interface `Transport` το δέχεται χωρίς αλλαγή στον `LinkProbe`.
