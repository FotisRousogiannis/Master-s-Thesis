# ADR-0016: Στρώματα λογισμικού και εφαρμογή ελέγχου (GUI)

- **Κατάσταση:** Αποδεκτή
- **Ημερομηνία:** 2026-11-09

## Πλαίσιο
Χρειάζεται μια εφαρμογή από την οποία ο χρήστης ξεκινά το σύστημα, κινεί τον
βραχίονα και βλέπει την κατάστασή του (αρθρώσεις, αισθητήρες, κάμερα, πλακέτες),
ταυτόχρονα με την προσομοίωση (Gazebo) και την οπτικοποίηση (RViz). Απαιτήσεις του φοιτητή:
- τρία παράθυρα — προσομοίωση, RViz, κατάσταση/έλεγχος — **δυναμικά** (μετακίνηση,
  αλλαγή μεγέθους, μία ή δύο οθόνες, αποθήκευση διάταξης)·
- εκκίνηση από **εικονίδιο**, χωρίς γραμμή εντολών, σε Ubuntu και Windows·
- όλα μέσα στο Docker (ADR-0002)·
- σύνδεση με τον πραγματικό βραχίονα **με USB ή με WiFi**.

Ισχύουν οι κανόνες του `docs/architecture.md`: πάνω από το ros2_control υπάρχουν μόνο
λογικές αρθρώσεις, και προσομοίωση/πραγματικός βραχίονας διαφέρουν **μόνο** στο hardware interface.

## Εναλλακτικές

### Αρχιτεκτονική της εφαρμογής
1. **«Λεπτό» GUI** — καμία λογική ελέγχου μέσα του· μιλά μόνο μέσω ROS interfaces
   (topics, services, actions). Η λογική (ασφάλεια, καταστάσεις, IK) ζει σε nodes.
2. **«Παχύ» GUI** — η εφαρμογή περιέχει λογική (π.χ. δική της IK, όρια, καταστάσεις).
   Πιο γρήγορο στην αρχή, αλλά αν κλείσει/κρασάρει το GUI ο βραχίονας μένει σε άγνωστη
   κατάσταση, και η λογική δεν δοκιμάζεται ούτε επαναχρησιμοποιείται χωρίς αυτό.

### Τεχνολογία GUI
| Επιλογή | Υπέρ | Κατά |
|---|---|---|
| Πάνελ μέσα στο RViz (C++ plugin) | όλα σε ένα παράθυρο | μόνο C++, δεμένο με το RViz, αργή ανάπτυξη |
| Plugins rqt | έτοιμα εργαλεία, docking | εμφάνιση «εργαλείου εργαστηρίου», περιορισμένος έλεγχος |
| **Ανεξάρτητη εφαρμογή Qt σε Python** | πλήρης έλεγχος, Qt Designer, ίδιο Qt με RViz/rqt, ήδη στο image | όλα φτιάχνονται από εμάς |
| Web (rosbridge / foxglove_bridge + JS) | κινητό/tablet, χωρίς εγκατάσταση | δεύτερη γλώσσα, επιπλέον στρώμα, καθυστέρηση |
| Python dashboards (NiceGUI, Streamlit) | πολύ γρήγορο πρωτότυπο | αδύναμα για σύνθετη διεπαφή πραγματικού χρόνου |
| Game engine (Unity, Godot) | εντυπωσιακό 3D, VR | βαρύ, εκτός σκοπού |

Qt 5 (PyQt5 μέσω `python_qt_binding`, μέρος του `ros-jazzy-desktop`) ή Qt 6 (PySide6, εγκατάσταση
επιπλέον, δύο εκδόσεις Qt στο ίδιο σύστημα).

### Τρία παράθυρα
1. **Τρία ξεχωριστά παράθυρα** (Gazebo, RViz, GUI) που τα τοποθετεί το GUI.
2. **Ένα παράθυρο με ενσωματωμένα Gazebo και RViz** — το RViz ενσωματώνεται μόνο από C++,
   το Gazebo Harmonic είναι Qt 6 ενώ το RViz Qt 5· μένει μόνο η «αρπαγή» παραθύρων X11,
   εύθραυστη ειδικά σε XWayland (ADR-0010).

### Γλώσσα ανά κομμάτι
Όλα C++ · όλα Python · **ανάλογα με το κομμάτι**.

## Απόφαση

### Στρώματα
```
 Διεπαφή     arm_gui (Qt, Python) · RViz · Gazebo GUI
 ─────────── μόνο ROS interfaces ───────────────────────────────────────────
 Εποπτεία    arm_manager: καταστάσεις IDLE/MANUAL/AUTO/FAULT/STOP, ποιος κινεί τον βραχίονα
 Εργασίες    arm_tasks (pick & place) · arm_perception (RealSense → θέσεις αντικειμένων)
 Κίνηση      MoveIt 2 (IK, σχεδιασμός, συγκρούσεις) · MoveIt Servo (καρτεσιανό jog)
 Έλεγχος     ros2_control: joint_state_broadcaster, arm_controller (FollowJointTrajectory)
 Υλικό       hardware:=mock │ gazebo (gz_ros2_control) │ real (arm_hardware → micro-ROS → ESP32)
```
Επιλογή υλικού με **μία** παράμετρο: `ros2 launch arm_bringup bringup.launch.py hardware:=mock|gazebo|real`.

### Packages (`software/ros2_ws/src/`)
| Package | Ρόλος | Γλώσσα |
|---|---|---|
| `arm_description` | URDF, ros2_control tags, οπτικοποίηση | xacro |
| `arm_bringup` | controllers, launch με `hardware:=`, κόσμος Gazebo | launch / YAML |
| `arm_gui` | εφαρμογή ελέγχου | Python |
| `arm_interfaces` | δικά μας msgs/srvs (κατάσταση, αλλαγή mode) | msg/srv |
| `arm_manager` | εποπτεία, καταστάσεις, ασφάλεια σε επίπεδο λογισμικού | Python |
| `arm_moveit_config` | MoveIt 2 | YAML |
| `arm_hardware` | plugin ros2_control προς τα ESP32 | **C++** (υποχρεωτικά) |
| `arm_perception`, `arm_tasks` | όραση, pick & place | Python |

Κανόνας γλώσσας: **C++** όπου μετράει ο χρόνος ή το απαιτεί το framework (firmware, `arm_hardware`),
**Python** όπου μετράει η ταχύτητα ανάπτυξης (GUI, εποπτεία, όραση, εργασίες). Ένα node σε Python που
αποδειχθεί αργό στις μετρήσεις ξαναγράφεται σε C++ χωρίς αλλαγή στα υπόλοιπα (ίδια interfaces).

### Εφαρμογή ελέγχου (`arm_gui`)
- **Λεπτό GUI** σε **Python + PyQt5 μέσω `python_qt_binding`**· οι φόρμες μπορούν να σχεδιάζονται στο Qt Designer.
- Εσωτερικά: στρώμα γέφυρας ROS (`rclpy` σε δικό του thread → Qt signals)· τα widgets δεν ξέρουν ROS.
- Εντολές κίνησης μέσω του action `FollowJointTrajectory` (feedback, αποτέλεσμα, **ακύρωση**).
- Ονόματα και όρια αρθρώσεων διαβάζονται από το `/robot_description` → η εφαρμογή προσαρμόζεται
  μόνη της όταν το προσωρινό URDF (ADR-0009) αντικατασταθεί από το export του Fusion.
- **Τρία ξεχωριστά παράθυρα** (Gazebo, RViz, εφαρμογή). Η εφαρμογή τα τοποθετεί (`wmctrl`) με έτοιμες
  διατάξεις («Laptop», «2 οθόνες», «Χωρίς Gazebo») ή με διατάξεις του χρήστη· αποθηκεύει τη διάταξη στο
  κλείσιμο και την επαναφέρει, φέρνοντας μέσα στις οθόνες ό,τι θα έμενε εκτός (π.χ. αποσύνδεση δεύτερης οθόνης).
- Μέσα στην εφαρμογή: πάνελ (`QDockWidget`) που μετακινούνται, γίνονται καρτέλες, ξεκολλούν σε δικό
  τους παράθυρο ή κρύβονται — Σύστημα, Αρθρώσεις, Αισθητήρες, Log (και αργότερα Κάμερα, Καταστάσεις,
  Εργασίες). Το κουμπί **STOP** είναι στη γραμμή εργαλείων και δεν κρύβεται.
- Η εφαρμογή είναι **η ίδια** σε προσομοίωση και σε υλικό· ό,τι υπάρχει μόνο στο υλικό (υγεία ESP32,
  INA219, μαγνήτες AS5600) εμφανίζεται ανενεργό στην προσομοίωση.
- Το STOP της εφαρμογής είναι **λογισμικό** (ακύρωση τροχιάς, κράτημα θέσης) και **δεν** αντικαθιστά
  το E-stop υλικού στην τροφοδοσία των servo.

### Σύνδεση με τον βραχίονα: USB ή WiFi
Και τα δύο είναι επίσημα transports του micro-ROS (ADR-0006, ADR-0007) και επιλέγονται στην εφαρμογή
όταν `hardware:=real`:
| Σύνδεση | micro-ROS Agent | Docker |
|---|---|---|
| **WiFi** | `udp4 --port 8888` | ήδη: `network_mode: host` |
| **USB** | `serial --dev /dev/ttyACM*` (εγγενές USB του ESP32-S3) | πρόσβαση στο `/dev` με κανόνες cgroup για `ttyACM`/`ttyUSB` ώστε να λειτουργεί και η σύνδεση εν λειτουργία (hot-plug)· Windows: `usbipd` για να περάσει η συσκευή στο WSL |
Πάνω από τον Agent δεν αλλάζει τίποτα: τα ίδια topics, το ίδιο `arm_hardware`.

### Εκκίνηση με εικονίδιο
Script του host (`software/launcher/arm_studio.sh`) που σηκώνει το container, χτίζει το workspace αν
χρειάζεται και ανοίγει την εφαρμογή. Εικονίδιο: αρχείο `.desktop` στο Ubuntu, συντόμευση που καλεί το
`wsl.exe` στα Windows (εγκατάσταση με ένα script για το καθένα).

## Αιτιολόγηση
- Λεπτό GUI: ασφάλεια (η κατάσταση του βραχίονα δεν εξαρτάται από ένα παράθυρο), αντικαταστασιμότητα
  (web UI αργότερα χωρίς αλλαγές), κάθε λειτουργία ελέγχεται και από τερματικό (tests, κεφ. 8).
- Python + Qt 5: ήδη στο image, ίδιο Qt με RViz/rqt, γρήγορη ανάπτυξη· οι ρυθμοί του GUI (10–30 Hz)
  δεν απαιτούν C++. Το `python_qt_binding` κρατά τον κώδικα σχεδόν ίδιο σε μελλοντική μετάβαση σε Qt 6.
- Τρία ξεχωριστά παράθυρα: κάθε πρόγραμμα τρέχει όπως σχεδιάστηκε, κρασάρισμα του ενός δεν ρίχνει
  τα άλλα, με υλικό απλώς δεν ανοίγει το Gazebo.
- Όλο το σύστημα (όραση, pick & place, GUI) ολοκληρώνεται και μετριέται στο Gazebo όσο κατασκευάζονται
  οι πλακέτες· το υλικό «κουμπώνει» με `hardware:=real`.

## Συνέπειες
- Το image αποκτά `wmctrl` (τοποθέτηση παραθύρων) — χρειάζεται `docker compose build`.
- Η τοποθέτηση των παραθύρων Gazebo/RViz είναι «καλύτερη προσπάθεια»: εξαρτάται από τον window manager
  του host (GNOME/XWayland, WSLg). Αν αποτύχει, τα παράθυρα απλώς μένουν όπου τα έβαλε το σύστημα.
- Οι ρυθμίσεις της εφαρμογής (διατάξεις) αποθηκεύονται εκτός container (`.local/` στο repo, εκτός git),
  ώστε να μη χάνονται με το `docker compose down`.
- Το `hardware:=real`, ο micro-ROS Agent στο image, το `arm_manager` και τα επόμενα πάνελ ακολουθούν σε
  επόμενα βήματα, με τη σειρά: mock → GUI → Gazebo → manager → MoveIt → όραση → υλικό.
- Τα Windows (WSLg, Docker μέσα στο WSL, `usbipd`) δεν έχουν δοκιμαστεί ακόμα.
